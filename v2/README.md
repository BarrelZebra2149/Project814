# v2 — 구멍 개수 에너지로 BOJ 18789 "814 - 2" 탐색

8×14 숫자 격자에서 킹 이동(8방향, 같은 칸 재사용 가능)으로 읽을 수 있는 수 중 `1..K`가 전부 읽히는 최대 `K`를 찾는 문제입니다.
이 폴더는 기존 `school_linux_backup/sa814`(DEAP GA → SA/PT → 토너먼트) 방식을 버리고 **탐색의 목적함수를 바꾼** 새 접근입니다.

## 핵심 발견

- 점수 `K`(처음 못 읽는 수 − 1)를 직접 최적화하면 지형이 **절벽**입니다. K≈3100 격자에서 칸 하나를 바꾸면 83%가 K를 −1000 이하로 떨어뜨립니다
  (`move_hist.py`). 옛 에너지(`K + 0.002·look`, `look`은 K 바로 위 400개)도 같은 한계를 가집니다.
- 대신 **1..9999 중 읽을 수 없는 수(구멍)의 개수**를 에너지로 쓰면 지형이 매끄럽습니다. 칸 하나 변경의 구멍 개수 변화는 중앙값 +13~+29
  (`hole_smooth.py`, `reports/analyze_report.txt`).
- 구멍은 "이 수를 읽는 체인(걷기)이 몇 개이고, 그 체인들이 같은 칸에 몰려 있는가"로 **정확히** 계산할 수 있습니다(`engine.py`). 칸 하나를 바꾼 뒤의
  점수를 97.9% 정확히 예측하고 틀린 경우는 0건입니다(`fragility.py`).

## 실행

```bash
pip install numpy numba scipy scikit-learn
python gen_data.py --seconds 120 --workers 4 --out data_gen        # 테스트용 데이터
python test_engine.py data_gen && python test_moves.py data_gen    # 정확성 검증
python run.py --state state --out out --workers 7 --zero 5 --random 5
```

- 걷기 표(`tables*.npz`)는 첫 실행 때 자동 생성됩니다.
- `run.py`는 `state/state.json`이 있으면 자동으로 이어서 실행하고(`--fresh`로 새로 시작), 신규 최고는 `out/best.txt`에 `core814`로 재채점해 기록합니다.
- `verify_scorer.py`와 `fragility_hi.py`는 격자 텍스트 코퍼스 폴더가 필요하며 이 저장소에는 포함하지 않았습니다.

## 한계 (정직하게)

- A/B는 98개 중 28개만 돌고 중단했습니다(팔당 4~5시드). 구멍 에너지가 K 직접 최적화보다 낫다는 것은 확실하지만(p<0.01),
  연장·보강 이동이 순수 어닐링보다 낫다는 것은 **가능성만** 보였습니다. 급소 위험을 에너지에 넣은 팔은 돌리지 않았습니다.
- 5자리 엔진은 4자리보다 약 5배 느립니다. 9999를 넘는 격자는 한 개(10010)만 얻었고, 그 위로는 이제 막 올라가는 구간입니다.
- 처음 세운 "격자 요약 통계로 점수를 예측하는 ML"은 통계 검증에서 신호가 없어 만들지 않았습니다.
